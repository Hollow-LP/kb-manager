# 知识库管理平台 —— 项目总结（面试准备版）

> 说明：本文档用于面试准备。技术栈描述以「MySQL + PostgreSQL + Milvus + MinIO + MongoDB + Redis」的架构为准，
> 与仓库内实际代码的差异仅体现在存储选型，核心业务规则（权限模型、鉴权问答链、FAQ 闭环、缺口口径）与代码一致。
> 配套文档：`docs/DEVELOPMENT.md`（设计）、`docs/API.md`（接口）、`docs/DEMO.md`（演示）、`docs/FINETUNE.md`（微调）。

## 一、一分钟版本（自我介绍时用）

我做过一个面向企业内部的知识库管理平台，把「知识维护、四维数据权限、AI 鉴权问答、数据看板和知识沉淀」串成一个闭环。

核心难点有三个：

1. **AI 问答必须做到“按人鉴权”**：同一个问题，不同部门和角色的人问，智能体只能基于他有权访问的知识回答，无权访问的部分要明确提示；
2. **权限模型要从“功能权限”扩展到“数据权限”**：全局、部门、角色、个人四类实体可以混合配置，任意一种满足就能访问，并且随角色调整实时生效；
3. **知识要能自我沉淀**：从历史问答里自动挖掘高频问题生成候选 FAQ，审核发布后写入缓存加速；同时识别“知识库答不上来”的问题，形成知识缺口清单。

技术栈是前后端分离：后端 FastAPI + SQLAlchemy async，存储按职责拆分——MySQL 存业务主数据、PostgreSQL 存权限/切片/访问日志、Milvus 做向量检索、MongoDB 存会话消息、MinIO 存原始文档、Redis 做 FAQ 缓存；前端 Vue 3 + Element Plus + ECharts；大模型通过 OpenAI 兼容接口流式接入。

## 二、项目背景与目标

**背景**：企业内部制度、操作手册、产品资料分散在共享盘和 IM 里，员工找不到、找不准；同时存在“不同岗位能看的资料范围不同”的合规要求（比如财务审批权限手册只对财务和高管开放）。

**目标**：做一个平台，让知识能被集中导入与维护，让 AI 问答严格按数据权限作答，并且能从使用数据里持续改进知识库。

**角色**：

| 角色 | 职责 |
|---|---|
| 系统管理员 | 用户/角色/部门、菜单与按钮权限、看板 |
| 知识管理员 | 导入维护知识单元、配置数据权限、审核发布 FAQ、处理知识缺口 |
| 普通用户 | 登录并进行 AI 问答，只看到自己有权访问的知识 |

**存储职责划分（面试必问：为什么要这么多库）**

| 存储 | 存什么 | 为什么用它 |
|---|---|---|
| MySQL | 用户、角色、部门、角色权限、知识单元元数据、数据权限实体、FAQ、缺口的**主数据** | 团队最熟悉、事务与关联查询成熟、运维成本低；这些是强关系、强一致的数据 |
| PostgreSQL | 数据权限表、知识单元切片（chunk，含关键词全文索引 tsvector）、问答访问日志 | 权限判定与切片内容在一起，召回后可直接回库过滤并取正文；日志按日/周、Top 榜、P95 耗时用 SQL 窗口函数和 percentile 聚合很方便 |
| Milvus | 切片向量集合（chunk_id 与 PostgreSQL 切片一一对应） | 向量规模上来后（百万级以上）专用向量库的 HNSW/IVF/GPU 索引、批量写入和分区能力更适合大规模场景，可多集合并行召回 |
| MongoDB | 会话（sessions）与消息（messages），含引用列表、缺失单元 ID、流式状态 | 消息是半结构化的追加写文档，引用和缺失信息字段会持续演进；按会话查询天然适合文档模型，写入性能好 |
| MinIO | 原始上传文档（PDF/DOCX/MD/TXT）、附件、导入临时文件 | 对象存储适合大文件，和数据库解耦；容器化部署、S3 兼容，便于后续迁云或做 CDN |
| Redis | 已发布 FAQ 的精确匹配缓存、问题向量缓存；可选做导入任务队列 | 高频问题命中直接在毫秒级返回、不消耗 Token；队列做异步解析 |

**统一口径：向量召回 + 权限过滤如何配合**
Milvus 只负责“召回候选”，不做权限判断；召回拿到一批 chunk（对应 unit_id）后，回 PostgreSQL 的权限表按“全局/部门/角色/个人”计算哪些单元可访问，只有授权的单元内容才拼进 Prompt。这样权限规则只有一个真相来源（PostgreSQL），Milvus 里不需要冗余权限字段，也不会出现权限数据不同步。

## 四、技术栈与选型理由（高频追问题）

### 4.1 后端

| 技术 | 版本/说明 | 为什么选 |
|---|---|---|
| FastAPI | 异步、自带 OpenAPI 文档 | SSE 流式输出原生支持；依赖注入适合做鉴权链；Pydantic 校验减少脏数据 |

| motor / pymongo | MongoDB 客户端 | 异步读写会话消息 |
| minio-py | 对象存储 | 上传/下载原始文档 |

|---|---|

### 4.3 大模型相关

- **对话模型**：OpenAI 兼容接口，流式；关闭思考模式（`enable_thinking=false`），同问题耗时从约 15s 降到约 2s。
- **Embedding**：本地 `bge-small-zh-v1.5`（512 维），中文语义效果好、可离线；也可切远程接口。
- **Rerank**：qwen3-rerank 对候选重排，库外问题最高分从 0.4~0.5 降到 0.24~0.34，缺口识别明显更准。

## 五、核心模块与关键设计

### 5.1 认证与权限（RBAC）

- 登录返回 `access_token + user_info(部门/角色) + permissions[]`。
- 后端每次请求解析 JWT → 校验用户状态 → 查角色对应的权限码（如 `knowledge:unit:create`）→ 校验操作权限。
- **权限实时生效**：不在 token 里固化权限，而是每次从库里算，管理员改角色权限后对方下一次请求即生效。
- 前端：路由守卫按 `meta.permissions` 过滤菜单，`v-permission` 指令控制按钮显隐；**前端只做展示，后端必然二次校验**。

### 5.2 组织架构

- 部门树（父子关系、负责人、成员数）；用户多角色；角色权限树（菜单/按钮/AI 访问三种类型）。
- 部门删除前校验无子部门、无成员；用户不能停用/删除自己。

### 5.3 知识导入与解析

- 单文件/多文件上传，支持 PDF、DOCX、MD、TXT；整批先校验格式和大小，有非法文件整批拒绝，避免半批入库。
- 文件存 MinIO，元数据入 MySQL；后台 Worker 做“解析 → 按标题层级切片 → Embedding → 写 PostgreSQL 切片 + Milvus 向量”。
- **一个文档 = 一个知识单元**，单元内有多个切片；单元解析中不可被检索，完成后状态置为生效。
- 切片策略：识别“第X章/一、/（一）/1.2”等标题层级，路径拼进片段前缀（如 `【二、住宿标准】`），既保留语义又方便引用章节。
- 导入进度：任务状态（排队/解析/向量化/成功/失败）落库，前端轮询；服务重启后未完成任务自动重新入队。

### 5.4 数据权限（项目最核心）

- 每个知识单元可以配置四类权限实体：`global`（全局）、`department`（部门）、`role`（角色）、`user`（个人），支持混合。
- **默认无权限**：没配置任何实体的单元，任何人都访问不到（合规要求）。
- 判定逻辑：拿到用户所属部门 + 全部角色，用一条 SQL 做 OR 匹配：

```sql
SELECT DISTINCT up.unit_id
FROM unit_permissions up
WHERE up.unit_id IN (...)
  AND ( up.target_type = 'global'
     OR (up.target_type = 'department' AND up.target_id = :dept_id)
     OR (up.target_type = 'role'       AND up.target_id IN (:role_ids))
     OR (up.target_type = 'user'       AND up.target_id = :user_id) );
```

- **部门权限不向下继承**：配置“技术中心”只覆盖技术中心本身，研发部/运维部需要单独勾选。这是一个明确的业务决策（避免一个部门授权时意外放大范围）。
- 列表接口按 `scope=mine` 过滤；没有维护权限的用户就算传 `scope=all` 也会被强制降级，防止绕过。
- 管理端：知识管理员要能看到全部单元做维护，所以详情接口对持有维护权限的人放行——**但 AI 问答链路上的过滤不受影响**，仍然严格按数据权限。

### 5.5 AI 鉴权问答（SSE）

一段完整的链路（面试重点，建议能按顺序讲出来）：

```
用户提问
 → 1. 校验登录态（401）与 AI 访问权限（403）
 → 2. 会话：没有就新建，写入用户消息
 → 3. 精确 FAQ 缓存命中？命中 → 直接分块输出标准答案（Token=0），结束
 → 4. 检索召回：Milvus 向量召回 + PostgreSQL 关键词召回 → 重排（qwen3-rerank）→ 单元级聚合
 → 5. 调用数据权限引擎，得到 authorized / unauthorized 两组单元
 → 6. 只把 authorized 单元的片段按预算拼进 Prompt（不足阈值分的授权单元也不放进去）
 → 7. LLM 流式生成，SSE 推 delta
 → 8. 对召回但未授权的单元，发 missing 事件给前端展示"权限缺失卡片"
 → 9. 结束后写助手消息（MongoDB）与访问日志（PostgreSQL）：Token、耗时、命中/未授权单元
```

- **SSE 事件**：`meta → citation* → missing? → delta* → done`（失败时 `error`）。
- **为什么鉴权放在生成之前**：保证未授权内容从物理上不会进入 Prompt，而不是生成后再删——后者无法防止模型“顺着已看到的内容”泄露。
- **缺失提示**：召回里有未授权单元就提示（只给标题 + 编号，不含内容），可通过配置改成只提示数量。

### 5.6 检索与重排

- 向量召回：中文 Embedding，按余弦相似度取 topN。
- 关键词召回：pg_trgm/tsvector，弥补专有名词命中。
- 重排：对候选单元用交叉编码式 rerank 重新打分，低于阈值（0.55）的授权单元不进入 Prompt。
- 排序口径：**按单元最高相似度排序**。曾用 RRF 融合，但同一文档块多会把无关文档顶上去（问住宿标准时第一条是报销制度），改回按相似度后明显改善。

### 5.7 数据看板

- 数据来源：问答访问日志（每次问答追加一条）。
- 指标：Agent 访问次数、独立访问人数（UV）、知识单元数、Token 总量、平均响应时间（含 P50/P95）。
- 榜单：常见问题 TOP（问句规范化去重后聚合）、知识单元热度 TOP（引用次数 + 因权限拦截次数）。
- 趋势：按日/周访问趋势、Token 拆分趋势（prompt/completion）、响应时间直方图。
- 接入层：看板一次性聚合接口 `GET /dashboard/overview`，前端只发一个请求。

### 5.8 知识沉淀

**FAQ 挖掘 → 审核 → 缓存**

1. 定时（默认每天 02:00）或手动触发，扫描近 30 天问答日志；
2. 按问题向量聚类，频次 ≥ 3 生成候选 FAQ；
3. **排除两类脏数据**：回答是“未找到”的（库外问题，应做缺口）、没有任何授权资料的（回答只是“无权限”）；
4. 与已发布/待审 FAQ 语义重复的跳过；
5. 管理员审核可编辑标准答案，通过后写入 Redis 缓存；
6. 用户下次提问（去标点空格后）完全一致 → 直接返回标准答案，Token=0。

**知识缺口识别**

- 口径：本次没有任何可用资料（无授权单元，或因重排分低被过滤），**且模型回答是“未找到”**；
- “回答只是无权限提示”的不算缺口（属于权限问题）；
- 缺口按向量聚类归并，累计提问频次、保留样例问题；支持一键建档（把问题变成一篇知识单元），缺口自动置为已解决。

## 六、面试问答准备

> 每条给出「30 秒答法」，括号里是加分点。

### 6.1 项目与整体

**Q：简单介绍一下这个项目？**
A：见「一分钟版本」，重点讲三件事：鉴权问答、四维数据权限、知识沉淀闭环。

**Q：你负责哪部分？**
A：说清楚你主导的模块（建议选“权限模型 + 鉴权问答链路”或“数据看板 + 沉淀闭环”），其余讲协作边界。

**Q：项目难点是什么？**
A：① 权限要在 AI 链路里“召回之后、生成之前”生效，不能事后过滤；② 权限规则要从功能权限扩展到数据权限且实时生效；③ 问答效果要靠“检索质量 + 重排 + 拒答口径”一起调，不是只换模型。

**Q：为什么用这么多数据库？**
A：按数据形态和访问模式拆：主数据（MySQL，强关系强事务）、切片与日志（PostgreSQL，向量+关键词+聚合 SQL）、大规模向量（Milvus，专用索引）、会话消息（MongoDB，半结构化追加写）、原始文件（MinIO，对象存储）、缓存（Redis，毫秒级）。每个库只做它擅长的事；跨库用 ID 关联，权限只在 PostgreSQL 判定，避免多源真相。

### 6.2 权限相关

**Q：数据权限怎么设计的？**
A：单元维度挂权限实体表，四类实体 OR 匹配；默认无权限；一条 SQL 判定一批单元的授权/未授权；结果既给列表过滤，也给 AI 问答拼 Prompt 前使用。

**Q：为什么不用“部门继承”（上层部门能看到下级部门的知识）？**
A：继承会把授权范围意外放大（比如授权“总公司”就等于全员可见），不合规；我们的做法是显式勾选，需要子部门时一并勾选。

**Q：权限变更怎么做到实时生效？**
A：JWT 只放 user_id，角色和权限每次请求从库中查；数据权限每次问答现算。

**Q：前端隐藏按钮就安全了吗？**
A：不是，前端只做体验；所有写操作后端都有 `require_permission` 校验，数据权限在服务层统一计算。

**Q：管理员能看到所有单元，那普通用户会不会借此绕过？**
A：详情接口对“持有维护权限的管理员”放行是管理需要；普通用户没有维护权限，走的是数据权限校验；AI 问答链路对所有角色一视同仁地过滤。

### 6.3 AI 问答相关

**Q：怎么保证 AI 不看到无权访问的知识？**
A：先召回，再鉴权，再拼 Prompt。只有授权单元的内容进入上下文；未授权单元只在 `missing` 事件里给出标题提示。（加分：这是“物理隔离”，不是生成后删减。）

**Q：怎么保证回答有依据、不编造？**
A：三层：① Prompt 约束“只使用资料中明确写出的信息，资料里没有的数字不要推断”；② 重排过滤弱相关资料，不把无关内容塞进上下文；③ 评估时看幻觉率和引用准确率。（加分：做过 A/B，发现提示词较松时模型会把“超五千元双签”套到“五万元审批”上，收紧后明显改善。）

**Q：知识库答不上来的时候怎么办？**
A：资料为空或模型回答“未找到”时，后端判定为知识缺口并记录；回答会明确说“知识库中未找到相关信息”，不会编。（加分：起初用“检索分数低于阈值”判定，但引入重排后发现分数不低但没答案的情形漏判，后来改成按“回答是否有可用信息”判定。）

**Q：多个片段信息冲突怎么办？**
A：Prompt 要求只依据资料；冲突时模型会说明不一致点并分别引用；这类问题也会被统计进缺口，由知识管理员统一口径。

**Q：为什么用 SSE 而不是 WebSocket？**
A：这里是单向流式输出（服务端 → 浏览器），SSE 基于 HTTP、易穿透代理、断线重连简单；WebSocket 适合双向高频交互，这里用不上。

**Q：Token 是怎么统计的？**
A：直接解析模型接口的 SSE，在 `[DONE]` 前的 usage chunk 里读 prompt/completion；如果供应商不返回就按文本估算兜底。数据库加约束 `total = prompt + completion`，防止脏数据影响看板。

**Q：FAQ 缓存会不会返回不相关的答案？**
A：问答主链路只做**精确命中**（去标点空格后完全一致），语义相似的仍走知识库检索。这是有意为之——语义缓存容易出现近似但不同的问题拿到不相关答案。

**Q：怎么防止把“我不知道”沉淀成 FAQ？**
A：挖掘时排除两类：回答为“未找到”的库外问题、没有任何授权资料的无权限回答；这两类只归到知识缺口。

**Q：Embedding 和向量库怎么配合？**
A：切片时同时写 PostgreSQL（chunk 文本与元数据）和 Milvus（同 chunk_id 的向量）；召回从 Milvus 取候选，回 PostgreSQL 做权限过滤和内容拼装。（pgvector 可作为小规模时的兜底方案，同一套代码两种后端可切换。）

**Q：检索效果怎么调？**
A：先看召回命中（top1 是否相关），再加重排；排序从 RRF 改成“单元最高相似度”，解决块多的文档被顶上去的问题；阈值用真实问题集标定。

### 6.4 工程与数据

**Q：文档导入为什么异步？**
A：解析和向量化耗时，尤其是大 PDF；上传后立即返回 batch_id，Worker 后台处理，前端轮询进度；服务重启会把未完成任务重新入队。

**Q：文件存哪？**
A：原始文件进 MinIO，数据库只存对象路径和元数据；删除单元时软删除，保护日志和 FAQ 的外键引用。

**Q：看板的 UV、榜单怎么算？**
A：日志表按北京时间自然日聚合；UV 用 `count(distinct user_id)`；常见问题先规范化问句再聚合（“跨年发票能报销吗”和“跨年的发票能报销吗？”合并）；Token 和耗时按日和按周分组，缺失日期补 0 方便画趋势。

**Q：权限拦截次数怎么统计？**
A：日志里同时记录召回单元和授权单元，未授权 = 召回中不在授权列表里的部分；看板上这个数字能帮管理员发现“哪些单元应该开放权限”。

**Q：遇到过的坑？**
A：举两个：① 管理员列表能看到全部单元，但详情因数据权限被拦，导致打不开自己刚导入的单元，后来对维护权限放行、AI 链路照旧过滤；② 看板 Token 出现“总数不等于提示+生成”的脏数据，加数据库约束从源头堵住。

### 6.5 模型与效果

**Q：为什么还要微调？**
A：通用模型在“严格按资料回答、带引用、资料不足拒答”上不够稳；微调用知识库自己的问答样例提升忠实性和拒答能力。评估用同一批题目对比基线和微调后，看引用准确率、拒答正确率、幻觉率。（详细流程见 `docs/FINETUNE.md`。）

**Q：微调数据从哪来？**
A：线上问答日志（问题 + 当时召回 + 人工改写答案）、已审核 FAQ、文档本身构造的问答三元组，再按五类能力补样本；所有合成数据必须校验答案中的数字能在资料里找到。

## 八、可以继续优化的方向（面试官问“如果重做”时用）

1. 向量与权限分离后，可以做“按部门分区的 Milvus 集合 + 过滤字段”，减少无效召回；
2. 引入交叉编码重排已做，进一步可以加入“基于反馈的排序”（点击/追问数据）；
3. 知识缺口自动生成草稿知识单元，人工审核后一键入库，进一步缩短闭环；
4. 多租户化：权限实体增加 tenant 维度；
5. 观测：为每次问答打链路追踪（检索耗时、重排耗时、生成耗时分开统计）。
